# Easy3D architecture

This document describes implemented architecture. Future systems remain governed
by `MASTERPLAN.md` and must not be inferred as available from this document.

## Scene and entity ownership

Each public Python `Scene` exclusively owns one native C++ `World`. A `World`
stores entities in reusable slots and is authoritative for entity lifetime and
native entity state. A Python `Entity` is a small reference containing:

- a strong reference to its owning Python `Scene`, so the native world cannot
  disappear while a live wrapper still needs to query it; and
- a native `EntityHandle` with `world_id`, slot `index`, and `generation`.

The numeric public `Entity.id` combines generation and slot index. It is unique
within a scene for the lifetime of that entity, but it is not a network identity
and must not be serialized as one. Networking will assign separate stable IDs.

Destroying an entity increments the slot generation before the slot is reused.
Clearing a scene increments every live slot generation. Native access validates
all three handle fields, so stale and cross-world handles cannot alias newly
created entities. `is_alive` is a non-throwing probe; other stale-handle access
raises native `InvalidEntityError`, exposed to Python as a `ReferenceError`
subclass.

Entity names, `enabled`, `visible`, local TRS, hierarchy links, cached world
matrices, transform-dirty state, and optional singleton `RenderComponent` and
`LightComponent` values are native slot data. Component teardown occurs on
entity destruction, scene clear, and slot reuse.

Parent changes validate world ownership and reject cycles. Local matrices are
composed as translation × quaternion rotation × scale. Descendant caches are
invalidated recursively when any ancestor changes. Optional keep-world
reparenting calculates a new local TRS from the inverse parent matrix. Destroying
a parent detaches direct children with their world transforms preserved.

GLM 1.0.1 is an immutable, private implementation dependency for matrix and
quaternion operations. Public native and Python boundaries use Easy3D-owned
types so dependency representation changes cannot leak into gameplay code.

## Renderer and mesh resource ownership

`MeshData`, `Vertex`, `Bounds`, `Color`, and `Material` are Easy3D-owned native
types with no bgfx handles in their public representation. Mesh validation
rejects empty/non-triangular index streams, out-of-range indices, non-finite
attributes, zero normals, and invalid color channels. Built-in triangle, cube,
horizontal plane, and UV-sphere generators use counter-clockwise front faces,
right-handed coordinates, +Y up, and 32-bit indices.

The Win32 backend delegates to a private `BgfxRenderer`. Its internal
`MeshLifetimeManager` converts validated mesh data into one immutable vertex
buffer and 32-bit index buffer per resource. Move-only GPU mesh owners destroy
index and vertex handles deterministically. Renderer shutdown clears draw
items, releases all mesh buffers, programs, samplers, and material/lighting
uniforms, submits a final release frame, then shuts down bgfx before SDL destroys
the window.

The solid and textured shaders multiply vertex/texture RGBA by a material color
and optionally apply ambient plus Lambert directional illumination. The vertex
stage transforms normals with the inverse-transpose world matrix. Material state
controls lit/unlit selection, color/depth writes, `LESS` depth testing, and
counter-clockwise back-face culling. Easy3D-owned shader sources are
authoritative; reviewed D3D11 DXBC headers generated by the immutable-pinned
bgfx `shaderc` are committed so normal builds do not compile the complete
shader-tool dependency stack.

Phase 1.3 validation still provides an explicitly enabled native diagnostic
scene. Ordinary `Game` instances now pass their loaded native `Scene` to the
renderer. Each frame the renderer walks live handles, skips inactive, disabled,
invisible, and non-renderable entities, composes native world transforms, and
submits primitive meshes or OBJ parts. CPU mesh/model/image resources are
immutable and shared; private GPU buffers are cached by resource identity, while
GPU textures are keyed by image identity plus sampler settings. No per-frame
Python draw loop is involved.

Mesh AABBs are cached beside renderer resource identity. Each frame builds a
frustum from the capability-correct projection × view matrix and conservatively
tests a transformed bounding sphere before any texture upload or draw. Visible
items are grouped by mesh/material/texture. Groups of at least two uniformly
scaled instances use transient 4×4 model-matrix instance data and dedicated
instanced vertex programs; non-uniform scale uses the normal single-draw program
with an inverse-transpose matrix. Frame counters are published through a
sequence-protected set of atomics so Python monitoring cannot observe fields
from different frames.

## Camera and projection

The native `Camera` stores finite position, normalized quaternion orientation,
projection mode, vertical FOV or orthographic height, and positive near/far
planes with `far > near`. Its
right-handed basis uses local forward -Z, right +X, and up +Y. `look_at` rejects
coincident targets, zero up vectors, and direction/up parallelism.

`Matrix4` is an Easy3D-owned, column-major 4×4 value. Camera view matrices map
world space into camera space; perspective and orthographic projection both
select `[0,1]` depth for D3D or `[-1,1]` homogeneous depth when a future backend
reports that capability. Projection aspect is calculated from the current pixel viewport, not the
logical window size. SDL resize/pixel-size events update the bgfx swap chain and
view rectangle; each submitted frame rebuilds projection from the current pixel
width and height.

Python `Camera` is a typed configuration facade backed by the same native
view/projection/look-at math. It exposes mutable `Vec3` position/Euler rotation
and matrix tuples. Each native `Scene` owns a camera value, initialized to a
usable look-at default. Python assignment copies a `Camera` into the scene, and
the renderer reads it each frame while still deriving aspect from the current
pixel viewport. Cameras are not entities or components in this baseline.

## Lighting and debug rendering

Each world slot may own one validated `LightComponent`. Ambient components
accumulate color × intensity. The first enabled directional component derives a
world-space direction by rotating local -Z through the entity hierarchy; later
directional components remain stored but are not blended by the baseline. A
default ambient/directional rig remains for kinds that have no explicit scene
component, preserving visible output for simple scenes. Light and render
component mutation shares the same running-game guard as transforms.

`Scene` also owns persistent `DebugLine` values outside the entity registry.
The renderer groups them by depth-test mode, allocates frame-local transient
vertex buffers, and submits unlit line primitives through the solid program.
This establishes debug visualization without persistent GPU handles or
per-frame Python callbacks. Scene clear releases both entities and debug lines;
camera configuration remains reusable.

## Input ownership and frame boundaries

`Engine` owns one platform-neutral `InputSystem`; it has no SDL dependency and
is included in graphics-disabled builds. The Windows adapter translates SDL
physical scancodes, mouse motion/buttons/wheel, primary-gamepad buttons/axes,
connection changes, and window focus events into canonical `device:name`
controls. The action map combines those controls at `end_frame`, after all SDL
events for that frame have been drained.

Input state and action maps share a mutex because `Engine.run()` releases the
GIL and monitoring Python threads may request pointer lock or inspect state.
Focus loss zeros every held control and the window thread drops relative mouse
mode. A pointer-lock request remains declarative so focus gain can safely apply
it on the SDL-owning thread. No SDL object or event pointer crosses the native
boundary into Python.

## Asset and model ownership

`TextureCache` and `ModelCache` use canonical absolute paths (case-folded on
Windows) as deterministic keys. Texture keys additionally contain linear/sRGB
intent. Cache entries are immutable shared native allocations; clearing a cache
releases only its references. Mutex-protected lookup/load prevents duplicate
resources under concurrent requests. GPU texture and mesh handles remain
private renderer resources released before bgfx shutdown.

The pinned tinyobjloader dependency is private. Easy3D converts parsed OBJ/MTL
data into its own `ModelData`, material, part, and `MeshData` values. Parts are
triangulated and grouped by shape/material. Supplied normals are normalized;
missing normals become per-triangle flat normals. OBJ V is converted to the
engine's top-left UV convention. This model cache is graphics-independent so a
headless process can validate geometry without linking image decoders or bgfx.

## Scene activation and construction contexts

There is no implicit process-global scene. `Entity(scene=scene)` is explicit,
while `with scene:` uses a Python `ContextVar` to provide scoped construction
syntax that is safe across nested and asynchronous Python contexts. Leaving the
context restores the prior scene.

`Game.load_scene(scene)` establishes exclusive game ownership and activates the
scene. A scene cannot be loaded by two games simultaneously. Replacing or
unloading a scene deactivates it without deleting its entities; callers may opt
into clearing on unload. Closing a loaded scene is rejected. `Game` retains the
strong Python scene reference while the native `Engine`/renderer uses a
non-owning pointer, and scene replacement is rejected during `run()`.

## Threading status

Scene mutation is single-gameplay-thread state. The pybind frame bridge
releases the GIL while SDL owns the loop, reacquires it for one Python scheduler
callback after event polling, and returns before native renderer traversal.
`Game` records that thread and callback scope; scene/entity/component APIs allow
running-game mutation only inside that exact boundary. Worker, physics, and
networking systems must use future owned queues instead of mutating the world
from uncontrolled threads.

`SimulationScheduler` retains per-world/entity lifecycle state across repeated
runs. It clamps render delta, accumulates a configurable fixed step, caps
catch-up work, and records dropped time/overruns. Hook iteration uses snapshots;
destroy and clear requests queue until the phase boundary, where `on_destroy`
runs before native invalidation. Newly constructed scripts become eligible at
the next lifecycle preparation boundary.

Callback profiling uses Python's monotonic high-resolution clock and records
calls, total, maximum, and latest duration per hook. Fail-fast exceptions cross
the C++ frame bridge and unwind normal renderer/window RAII. Tolerant mode logs
the traceback once and quarantines that entity for the rest of its lifetime.

## Standalone gameplay utilities

State machines, timers, cooldowns, event dispatch and tweens are pure Python and
do not import the native extension directly. They are deliberately caller
driven: the scheduler does not keep a global timer list or hidden event bus.
Scripts advance simulation-domain objects in `fixed_update`, render-domain
objects in `update`, and explicitly poll wall-domain objects. This preserves
world ownership and makes the utilities usable in headless tests and later
server contexts.

All dispatch is synchronous on the calling gameplay thread. State-machine
callbacks have a reentrancy guard; event dispatch snapshots ordered listeners
and bounds recursive depth. These constraints avoid partially nested state
transitions and unbounded event recursion without introducing worker threads or
an implicit process-global service.

## Physics ownership and fixed stepping

Jolt 5.6.0 is statically linked behind a Pimpl boundary, with CPU/GPU compute,
object streams, debug renderer and profiler disabled. The build uses baseline
SSE2 rather than producing an AVX-specific wheel. Easy3D registers Jolt's global
allocator/factory/types once, while each lazily initialized `Scene` owns a
separate `PhysicsSystem`, layer filters, fixed temporary allocator and
single-threaded Jolt job system. The latter is a correctness-first foundation;
an engine job-system adapter can replace it only after owned worker shutdown and
profiling requirements are defined.

Physics body handles repeat the entity handle safety model with world ID, slot
and generation. A scene clear destroys every added Jolt body before its physics
system and invalidates all handles. Jolt resources contain no renderer state and
the complete falling-body/collision/lifetime regression runs in the
graphics-disabled build.

The scheduler's fixed phase is currently `Python fixed_update → deferred
mutation commit → native CharacterVirtual motor updates → Jolt
PhysicsSystem::Update → dynamic/character entity pose sync →
collision/trigger snapshot dispatch → deferred mutation commit`. Render updates
remain after all catch-up physics ticks.

`Scene` owns a generation-qualified entity-to-body table. Collider creation
builds a static Jolt body from the entity world pose; attaching/removing a rigid
body transactionally replaces that body with dynamic/kinematic or static
motion. Entity destruction removes the body before invalidating the entity.
Static and kinematic entity changes push pose into Jolt, while dynamic pose
changes are accepted only through the explicit teleport API and otherwise flow
from Jolt to the entity after a step. Physics entities reject parenting until a
local/world solver synchronization contract is implemented.

## Physics queries and contact dispatch

Narrow-phase ray, sphere/capsule cast and box/sphere overlap queries execute
synchronously against a scene's Jolt world. Jolt IDs are converted immediately
to generation-checked entity handles; collector storage never crosses the
binding boundary. Native results apply layer/sensor/exclusion filters before
conversion and deterministic sorting.

The Jolt `ContactListener` never calls Python. It copies only user IDs,
world-space contact data, phase and sensor state into a mutex-protected bounded
queue. Queue overflow is surfaced as `PhysicsError` when drained rather than
silently dropping an unbounded workload. The scheduler drains after each
completed physics update and dynamic-pose sync, builds immutable per-recipient
events, invokes callbacks through the existing exception/profiling path, and
commits deferred mutations afterward.

Contact reconciliation tracks which pairs were actually touched each step.
Pairs retired only because all moving bodies slept remain logically active, so
sleep does not fabricate an exit; an awakened pair that is no longer detected
produces the deferred exit snapshot.

## Character motor ownership

Each scene stores generation-qualified entity-to-character records beside its
body records. The physics Pimpl owns Jolt `CharacterVirtual` instances and a
smaller kinematic inner capsule on the character layer. The public handle never
contains a Jolt pointer. Character teardown precedes ordinary body teardown so
Jolt can safely remove the inner body during scene clear.

Input is compact native state: local right/forward movement, camera heading,
and a one-shot jump bit. Per fixed step, the motor applies acceleration or air
control, ground velocity, jump and gravity, clamps velocity against steep
slopes, selects first-person heading or third-person movement-facing rotation,
then calls `ExtendedUpdate` with explicit stair/floor distances. Only the
resulting position, rotation, velocity and ground snapshot cross into scene or
Python state. No Jolt callback invokes Python.
