# Easy3D architecture

This document describes implemented architecture. Future systems remain governed
by `MASTERPLAN.md` and must not be inferred as available from this document.

## Scene and entity ownership

Each public Python `Scene` exclusively owns one native C++ `World`. A `World`
stores entities in reusable slots and is authoritative for entity lifetime and
native entity state. A Python `Entity` is a small reference containing:

- a strong reference to its owning Python `Scene`, so the native world cannot
  disappear while a live wrapper still needs to query it; and
- a native `EntityHandle` with `world_id`, slot `index`, and `generation`.

The numeric public `Entity.id` combines generation and slot index. It is unique
within a scene for the lifetime of that entity, but it is not a network identity
and must not be serialized as one. Networking will assign separate stable IDs.

Destroying an entity increments the slot generation before the slot is reused.
Clearing a scene increments every live slot generation. Native access validates
all three handle fields, so stale and cross-world handles cannot alias newly
created entities. `is_alive` is a non-throwing probe; other stale-handle access
raises native `InvalidEntityError`, exposed to Python as a `ReferenceError`
subclass.

Entity names, `enabled`, `visible`, local TRS, hierarchy links, cached world
matrices, transform-dirty state, and an optional singleton `RenderComponent` are
native slot data. Component teardown occurs on entity destruction, scene clear,
and slot reuse.

Parent changes validate world ownership and reject cycles. Local matrices are
composed as translation × quaternion rotation × scale. Descendant caches are
invalidated recursively when any ancestor changes. Optional keep-world
reparenting calculates a new local TRS from the inverse parent matrix. Destroying
a parent detaches direct children with their world transforms preserved.

GLM 1.0.1 is an immutable, private implementation dependency for matrix and
quaternion operations. Public native and Python boundaries use Easy3D-owned
types so dependency representation changes cannot leak into gameplay code.

## Renderer and mesh resource ownership

`MeshData`, `Vertex`, `Bounds`, `Color`, and `Material` are Easy3D-owned native
types with no bgfx handles in their public representation. Mesh validation
rejects empty/non-triangular index streams, out-of-range indices, non-finite
attributes, zero normals, and invalid color channels. Built-in triangle, cube,
horizontal plane, and UV-sphere generators use counter-clockwise front faces,
right-handed coordinates, +Y up, and 32-bit indices.

The Win32 backend delegates to a private `BgfxRenderer`. Its internal
`MeshLifetimeManager` converts validated mesh data into one immutable vertex
buffer and 32-bit index buffer per resource. Move-only GPU mesh owners destroy
index and vertex handles deterministically. Renderer shutdown clears draw
items, releases all mesh buffers, the shader program, and its material uniform,
submits a final release frame, then shuts down bgfx before SDL destroys the
window.

The solid-color shader multiplies per-vertex RGBA by a material color. Material
state controls color/depth writes, `LESS` depth testing, and counter-clockwise
back-face culling. Easy3D-owned shader sources are authoritative; reviewed D3D11
DXBC headers generated by the immutable-pinned bgfx `shaderc` are committed so
normal builds do not compile the complete shader-tool dependency stack.

Phase 1.3 validation still provides an explicitly enabled native diagnostic
scene. Ordinary `Game` instances now pass their loaded native `Scene` to the
renderer. Each frame the renderer walks live handles, skips inactive, disabled,
invisible, and non-renderable entities, composes native world transforms, and
submits primitive meshes or OBJ parts. CPU mesh/model/image resources are
immutable and shared; private GPU buffers are cached by resource identity, while
GPU textures are keyed by image identity plus sampler settings. No per-frame
Python draw loop is involved.

## Camera and projection

The native `Camera` stores finite position, normalized quaternion orientation,
vertical FOV in degrees, and positive near/far planes with `far > near`. Its
right-handed basis uses local forward -Z, right +X, and up +Y. `look_at` rejects
coincident targets, zero up vectors, and direction/up parallelism.

`Matrix4` is an Easy3D-owned, column-major 4×4 value. Camera view matrices map
world space into camera space; projection selects `[0,1]` depth for D3D or
`[-1,1]` homogeneous depth when a future backend reports that capability.
Projection aspect is calculated from the current pixel viewport, not the
logical window size. SDL resize/pixel-size events update the bgfx swap chain and
view rectangle; each submitted frame rebuilds projection from the current pixel
width and height.

Python `Camera` is a typed standalone configuration facade backed by the same
native view/projection/look-at math. It exposes mutable `Vec3` position/Euler
rotation and matrix tuples. It is not yet a scene `Entity` or render component;
the Phase 1.7 scene renderer temporarily uses a fixed native look-at camera.

## Asset and model ownership

`TextureCache` and `ModelCache` use canonical absolute paths (case-folded on
Windows) as deterministic keys. Texture keys additionally contain linear/sRGB
intent. Cache entries are immutable shared native allocations; clearing a cache
releases only its references. Mutex-protected lookup/load prevents duplicate
resources under concurrent requests. GPU texture and mesh handles remain
private renderer resources released before bgfx shutdown.

The pinned tinyobjloader dependency is private. Easy3D converts parsed OBJ/MTL
data into its own `ModelData`, material, part, and `MeshData` values. Parts are
triangulated and grouped by shape/material. Supplied normals are normalized;
missing normals become per-triangle flat normals. OBJ V is converted to the
engine's top-left UV convention. This model cache is graphics-independent so a
headless process can validate geometry without linking image decoders or bgfx.

## Scene activation and construction contexts

There is no implicit process-global scene. `Entity(scene=scene)` is explicit,
while `with scene:` uses a Python `ContextVar` to provide scoped construction
syntax that is safe across nested and asynchronous Python contexts. Leaving the
context restores the prior scene.

`Game.load_scene(scene)` establishes exclusive game ownership and activates the
scene. A scene cannot be loaded by two games simultaneously. Replacing or
unloading a scene deactivates it without deleting its entities; callers may opt
into clearing on unload. Closing a loaded scene is rejected. `Game` retains the
strong Python scene reference while the native `Engine`/renderer uses a
non-owning pointer, and scene replacement is rejected during `run()`.

## Threading status

Scene mutation is currently single-gameplay-thread state. The registry does not
claim concurrent mutation safety. The public Python scene/entity/component APIs
therefore reject mutation while an owning `Game` is running and the renderer is
traversing the registry. Future gameplay, worker, physics, and networking systems
must communicate through the Phase 2 safe-boundary scheduler or owned queues
instead of mutating the world from uncontrolled threads.
